## ✅ M-GOOGLE-CHAT-SHOWS-THE-ASSISTANT-IS-WRITING-1 — a Google Chat conversation shows its message was seen and an answer is coming

**Why:** asked by the operator on 2026-09-29 after the Chat tests: Google Chat shows neither that the
assistant read the message nor that it is writing, while Discord shows both (a 👀 reaction on receipt,
`discord-adapter.ts:84`, and the typing indicator, `typing-keepalive.ts`). Google allows a reaction only
under user authentication (`spaces.messages.reactions.create`), which a Chat app does not hold, and its
Chat API has no typing indicator; an app may update and delete the messages it wrote itself.

**Tasks:**
- [x] On an incoming message the app posts one short line saying the assistant is writing, and deletes it when the first part of the answer is sent, or when the turn ends with nothing to say
- [x] The answer arrives as a new message, so the phone's notification shows the answer rather than the placeholder
- [x] Test: unit — the placeholder is posted once per turn and always removed, on success, failure and timeout

**Done when:** a person on Google Chat sees within a second that the assistant is on it, and only the answer stays.

## Out of scope for v0.1 (deferred)

- **Slack / Telegram adapters** — Tier-0 only, by customer request.
- **Multi-bot per agent** — one bot per template is the PoC contract.
- **Persistent session-store across container redeploys** — v0.1
  relies on mem0 + the persisted workspace inside the agent container
  to recover continuity on the next user turn. A dedicated
  session-store (à la OpenACP) is a v0.2 concern.
- **Skill command pinning, slash commands, button-based permission
  approval** — explicit UX-incompatibility per cerase M2 rules.
- **Doctor checks** — deferred; structured pino logs cover the PoC
  observability need.
